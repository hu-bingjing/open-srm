# Phase 04 实现设计

追加 V5，保留 V1–V4、原账号、订单快照和同步数据。实现供应商按计划行部分确认、交期确认/延期申请、采购审批和派生交货计划，不提供通用改状态或改数量接口。

## 权限与数量

读沿用 order.read 的同元组行权限，历史也按当前订单可见及历史工厂范围过滤。SUPPLIER 增加 confirmation.submit 动作，仍需同名组织范围、order.read 范围及正确供应商绑定；BUYER 增加 delivery.approve 动作，仍需同名范围和订单读取范围。ADMIN 不隐含供应商提交或采购审批能力。供应商角色继续与内部角色互斥，服务层另有申请人不能自批守卫，防止误配置动作权限后自批。

每个当前计划行按精确十进制计算：已生效确认 C、待审批确认 P，必须 C+P≤订购量 Q。未确认余额=Q−C−P。待审批数量预占，拒绝/撤回释放；改单交期不重复预占既有有效确认数量。写入继续复用实例行锁，权限、版本、数量、业务状态、审计、outbox 和幂等结果同事务。

确认 POST 以订单 If-Match 和来源版本为条件。按期/提前承诺直接 EFFECTIVE，自动生成等量 PLANNED 交货计划；晚于 ERP 要求日期时必须填写原因，确认 SUBMITTED，并同事务产生 INITIAL 延期申请，尚不生成交货计划。

## 审批及承诺变更

采购审批 INITIAL 延期：批准使确认 EFFECTIVE、采用批准交期并生成等量计划；拒绝使确认 REJECTED、释放数量。供应商仅可撤回本人待审批申请，INITIAL 确认随之 REJECTED。
已有 EFFECTIVE 确认可申请 RESCHEDULE（提前/延期均审批），原承诺和计划在批准前保持有效。每个确认至多一个待审批变更。批准时校验确认版本，旧计划 SUPERSEDED、新计划等量，原确认采用新交期并增加版本；拒绝/撤回保留原承诺。采购不能改申请数量或任意改承诺日期。审批事件不可变且每申请只有一项终态审批；重复决策只能通过合法幂等重放取得原结果。

所有变更增加订单本地版本；审批/撤回还校验申请 If-Match。幂等重放前重新检查当前组织/供应商权限、当前来源版本、有效状态及冻结条件；不会凭缓存泄露撤权或旧版本数据。

## ERP 变更与事件

接受新订单版本（包括取消/关闭/移除行）时，在同一导入事务中将旧版本 SUBMITTED/EFFECTIVE 确认、待审批交期申请和 PLANNED 交货计划 SUPERSEDED，保留数量、日期、已完成审批及源快照。重复来源事件不重复失效。来源冲突使订单一致性冻结，已有承诺保留为历史证据，阻止新增/审批/改单等写入，并停止相关待发内部事件。

outbox 本阶段为持久内部事件账本 PENDING/SUPERSEDED，仅记录必要业务引用，不调用 ERP 发布或发送外部消息。通知分发在 Phase 07，ERP 确认/ASN 发布仍关闭。Phase 05 尚未实现发货/收货，不能以交货计划等同实际发货或收货；上线 Phase 05 前必须增加已发货/已收货保护及版本对账。

## 验收

真实 PostgreSQL/HTTP 覆盖 100=60+40 部分确认、多计划行、待批预占、超量/零量/精度、并发竞争、过期 If-Match/来源版本、越公司/工厂/采购组织/供应商、冻结、申请人自批防御、拒绝/撤回/重复审批、有效承诺改期、版本导入联动、审计/outbox/幂等原子性、撤权后重放拒绝。浏览器使用独立虚构公司和供应商账号实际提交、采购审批、查看计划和版本失效。原测试实例先备份，隔离全量回归通过后升级并复验、重启及原数据摘要比对。
